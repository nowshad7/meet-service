# Operations

Day-to-day running of a deployment.
Every command takes the deployment name and works the same with `MEET_DEPLOYMENTS_DIR`.

## Health

```bash
scripts/meet health acme
tests/stack-check.sh acme
```

`health` shows container state and checks Prosody's `/health`, JVB's `/about/health` and that Jicofo sees at least one operational bridge; it exits non-zero on any failure, so it fits a cron job or a monitoring probe.
`tests/stack-check.sh` runs `health` and also checks that every enabled plugin is loaded on the right Prosody host, that Prosody logged no errors for them, that `/kick-user` answers and that the ban hook sits on the MUC component.
Run it after every `up`, upgrade or settings change.

## Logs

```bash
scripts/meet logs acme --since 1h prosody
scripts/meet logs acme -f jicofo jvb
```

| Look for | Where |
|---|---|
| Token rejected, key fetch failed | `prosody`: `token_verification`, `asap` |
| Room gate calls and answers | `prosody`: `reservations` |
| Webhook retries | `prosody`: `meet_events`, `API Response code` |
| Removals, bans | `prosody`: `mod_meet_control` |
| No bridge, conference allocation | `jicofo` |
| ICE failures, one-way media | `jvb`, and `JVB_ADVERTISE_IPS` |
| Recording uploads | `/storage/logs/recording-finalize.log` in `jibri` |

Docker keeps container logs with its default driver; configure log rotation in `/etc/docker/daemon.json` on long-running hosts.

## Backups

What to keep, per deployment:

| Item | Why |
|---|---|
| `deployment.env`, `brand/`, `compose.yml`, `lang/` | The deployment itself; keep them in git (this repository or `MEET_DEPLOYMENTS_DIR`) |
| `secrets.env` | XMPP passwords and `MEET_APP_API_TOKEN`; store it in your secret manager, never in git |
| `<CONFIG>/web/keys/` and `<CONFIG>/storage/web/` | Your own TLS certificate, or the Let's Encrypt account and certificates (`acme.sh`, `acme-certs`) |
| Recordings that failed to upload | `<CONFIG>/storage/jibri/recordings/` (see below) |

Everything else under `<CONFIG>` is regenerated by the containers from the settings, and meetings themselves hold no state worth restoring.
To restore, check out the release tag, put the deployment folder and `secrets.env` back, run `scripts/meet init <name>` (it keeps existing secrets) and `scripts/meet up <name>`.

## Recordings

With `MEET_FEATURES=recording`, each finished recording is uploaded to the app and then deleted from the recorder.
Uploads retry for about 15 minutes; after that the files stay in `<CONFIG>/storage/jibri/recordings/<key>/` on the host and the log says `giving up`.
Re-run a failed upload by hand once the app is reachable:

```bash
scripts/meet compose acme exec jibri ls /storage/recordings
scripts/meet compose acme exec jibri /usr/local/bin/meet-finalize.sh /storage/recordings/<key>
```

Watch disk space on the recordings volume; one hour of 720p is roughly 0.5 to 1 GB.
One Jibri records one meeting at a time, so run one per concurrent recording with `scripts/meet up acme --scale jibri=N`.

## Restarting and updating settings

| Change | Apply with |
|---|---|
| `deployment.env` | `scripts/meet up acme` (recreates the containers whose settings changed) |
| Brand static files | `scripts/meet up acme` |
| `custom-interface_config.js` | `scripts/meet up acme`, then `scripts/meet compose acme restart web` |
| A plugin file in `prosody/plugins/` | `scripts/meet compose acme restart prosody` (this ends every live meeting) |
| New release tag or Jitsi version | See [upgrade.md](upgrade.md) |

`scripts/meet down acme` stops a deployment and keeps its data; `down -v` is refused because it would delete all Jitsi state.
